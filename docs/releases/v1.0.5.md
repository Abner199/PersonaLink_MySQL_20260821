# PersonaLink MySQL v1.0.5 发布说明

发布日期：2026-09-08

## 修复问题

管理员班级页可能显示某班已有 46 名学生，但打开“查看学生”长时间等待后却显示“该班级暂无学生”。原因有两层：

1. 旧名单接口返回每名学生的完整 base64 头像和资料，大班级响应过大，容易超时。
2. 后端升级重启会使内存中的管理员令牌失效；前端把超时或 401 请求失败继续按空数组渲染，造成“没有学生”的错误判断。

## 优化内容

- 名单接口只返回姓名、邮箱、注册时间、头像索引等必要字段。
- 已存头像返回按需图片 URL，不在名单 JSON 中内嵌 base64。
- 加载失败时显示真实错误和“重新加载”按钮；只有成功返回空数组才显示“暂无学生”。
- 46 人全部带头像的模拟名单响应为 13,600 字节。
- CI 同时运行路由单元测试和真实 MySQL 查询测试。

## 数据安全

没有数据库表结构变化，不需要迁移。班级、学生、账号、密码哈希和头像数据原样保留。生产服务器不得执行 `npm run db:migrate-json` 或 `npm run db:schema`。

## 服务器升级

选择使用人数较少的时间执行：

```bash
# 进入项目并确认工作区无输出。
cd /srv/personalink
git status --short

# 获取并部署固定版本；脚本会先备份并比对 MySQL。
git fetch --tags origin
sudo /usr/local/sbin/deploy-personalink-release v1.0.5
```

升级会重启后端，管理员需要退出并重新登录，再打开班级名单。成功输出必须包含 `发布成功：v1.0.5；MySQL 数据清单保持一致。`。

## 生产部署验证记录

2026-09-09，生产服务器使用统一发布脚本从固定标签升级至 `v1.0.5`。现场结果如下：

- 发布脚本完整执行 `[1/9]` 至 `[9/9]`，健康接口和版本接口均返回 `1.0.5`。
- 升级前后 MySQL 的 11 项清单一致：7 个班级、89 个账号、88 名学生、9 个同义词组、116 个标准爱好、50 份已存头像和 1,505,310 字节头像数据全部保留，孤立账号为 0。
- `personalink`、Nginx 和 MySQL 均处于 active 状态，Nginx 配置检查通过。
- 本机照片墙返回 HTTP 200、37,509 字节、约 0.017 秒；HTTP 公网站点返回 HTTP 200、37,509 字节、约 0.016 秒。
- 只读巡检通过后，服务器无需再次部署，也无需恢复数据库。

升级重启后，旧管理员令牌会失效。若公开接口正常，但浏览器中的“查看学生”等受保护页面仍打不开，应退出管理员账号并重新登录；若页面仍保留旧状态，再清理 `peaceinside.fun` 的站点缓存或使用无痕窗口重新登录。现场完成会话刷新后，用户确认网页和学生名单恢复正常。

这类现象是浏览器会话或缓存问题，不是学生数据丢失。不得为此执行 `npm run db:migrate-json`、`npm run db:schema` 或数据库恢复。
